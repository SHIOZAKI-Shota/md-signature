md-signature は、.md ファイルに電子署名を埋め込むためのオープンな形式です。署名はファイル末尾の HTML コメントに入るので、表示は何も変わらず、ファイルは1つのまま。あとから何人でも連署できます。

md-signature の意義

文書と署名を1つのファイルにまとめると、AI を含む自動化の安全性、記録の持ち運び、長期の検証が同時に成り立ちます。

  1. 契約業務に非プロプライエタリ

    PDFのような独自形式ではなく、Markdownは誰でも読めるテキストです。署名に使う鍵は手持ちの SSH 鍵や自分で生成したキーで足り、有料の証明書や電子契約サービスの契約は不要です。

  2. 脱プラットフォーム・データの自己完結

    署名は文書の中にあります。サービスの解約や事業終了、アカウントの削除があっても、ファイルさえあれば検証を継続できます。仕様は CC0、実装はオープンソースです。

  3. 時刻証明と長期の証拠性

    RFC 3161 のタイムスタンプで、その時点に署名が存在したことを第三者の時刻認証局が証明します。署名者が申告する時刻と違い、後から書き換えられません。将来 Ed25519 が危殆化しても、耐量子署名を追記すればチェーン全体を保護できます。

  4. 発行元が署名した証明書

    大学や企業が、自組織のドメインの DNS に公開した鍵で修了証や在籍証明に署名できます。受け取った側は、その組織が発行したものかを自分で確認できます。Verifiable Credentials を簡素にした使い方です。

  5. 承認ワークフロー

    稟議、契約、仕様変更、リリース判定など、承認が必要な手順を文書だけで進められます。require に必要な承認者を宣言し、各担当者が順に連署します。CI やブランチ保護で mdsig verify を実行すれば、全員の署名が揃うまで次の工程に進みません。

  6. Git で扱える合意記録

    署名の追加はファイル末尾への追記なので、差分が読みやすく、誰がいつ何に署名したかを PR でレビューできます。履歴の書き換えも署名の検証で検出されます。

  7. AI エージェント指示書の改ざん防止

    CLAUDE.md や AGENTS.md に署名し、実行環境（フックや CI）が読み込み前に mdsig verify で照合します。PR や再配布の過程で書き換えられた指示書は、エージェントが読む前に拒否されます。ツールの出力や Web ページ経由の注入は対象外です。

  8. AI と人間の協調（Human-in-the-loop）

    AI が生成・修正した文書や設定に、責任者がパスキーや SSH 鍵で連署するまで、CI は適用を保留します。require に指定した連署が揃わない間、mdsig verify は終了コード 5 を返します。

  9. RAG・ナレッジベースの汚染対策

    取り込み処理で、承認者（role: approver）の有効な署名がある文書だけを索引に登録します。偽の文書や途中での改変は検知できます。承認者自身の判断の誤りまでは防げません。

  10. 添付ファイルまで含めた証跡

    スクリーンショットやデータファイル、リモートの画像をハッシュで固定します。本文だけでなく、参照先の差し替えも検知できます。

  11. 機密文書を外部に出さない

    検証も署名もブラウザ内またはローカルの CLI で完結し、文書をサーバーへ送信しません。tofu 方式ならネットワーク接続なしでも検証できます。

電子署名としての法的な扱いは、使用する鍵、運用、適用される法令によって異なります。

          署名ブロックの形式
          
                
          署名ブロックは、<!-- md-signature の行で開始し
                    --> の行で終了する HTML コメントです。内部には key: value
                    形式のフィールドを1行に1つずつ記述し、文書の末尾に配置します。
          
            
          
            
          
                
          
                    
          
                        
                            
          
                                キー
                                要否
                                内容
                            
          
                                  
                        
                            
          
                                v
                                必須
                                仕様のバージョン。本書の版は 0.0.1。
                            
          
                            
          
                                method
                                必須
                                
                                    公開鍵の解決方法。dns・git-hosting・pgp・tofu
                                    のいずれか。
                            
          
                            
          
                                signer
                                必須
                                署名者の識別子。構文は method
                                    に依存する（github.com/alice、example.com など）。
                            
          
                            
          
                                ts
                                必須
                                
                                    署名者が申告する署名時刻（UTC、YYYY-MM-DDTHH:MM:SSZ）。申告値にすぎず、第三者の証拠にはならない。
                            
          
                            
          
                                hash
                                必須
                                対象スライスのダイジェスト。sha256: に続けて小文字の16進数。
                                
                            
          
                            
          
                                sig
                                必須
                                署名対象ペイロードに対する署名。base64:
                                    に続けてパディング付きの標準 base64。
                            
          
                            
          
                                alg
                                任意
                                署名アルゴリズム。省略時は ed25519。
                            
          
                            
          
                                role reason
                                任意
                                役割（推奨値は
                                    author・reviewer・approver・witness）と、自由記述の理由。
                            
          
                            
          
                                selector key_fp pubkey
                                    fpr
                                条件付き
                                方式ごとの鍵情報（「公開鍵の解決」で説明）。
                            
          
                            
          
                                rp_id webauthn_*
                                条件付き
                                alg が
                                    webauthn-es256 の場合は必須、それ以外の場合は記述不可。

                                    resources revocation_url tsa_*

                                期限・部分署名・必須連署・リソース・撤回・タイムスタンプの拡張（「拡張フィールド」で説明）。
                                
                            
          
                            
          
                                x_*
                                任意
                                私的利用の拡張。意味は規定されないが、署名対象ペイロードに含まれる。
                            
          
                                  
                    
          
                
          
                
          
                    
                    
          構文規則
          
                    
            
                        
          1. 開始行は <!-- md-signature、終了行は
                            --> のみで構成する。フィールドの順序は任意で、同じキーの重複は malformed。
            2. 
                        
          2. 空行を含めない。CommonMark は空行で HTML ブロックを終了するため、以降の行が表示されてしまう。
            3. 
                        
          3. 値に -- と制御文字を含めない。--
                            はコメントを途中で終了させ、可視の Markdown を注入される原因になる。生成者はこの入力を修正せず拒否する。
            4. 
                        
          4. key: | と2スペース字下げの継続行で折り返し値となり、各行を
                            LF で連結して扱う。リストと、76文字を超えるバイナリ値に使用する。
            5. 
                        
          5. 本書で未定義のキーは
                            malformed（unknown-field）。x_ で始まるキーのみ例外。将来の拡張を解釈しない検証者による誤判定を防止する。

          仕様書 §3 署名ブロックの構文
          
        
          

        
          
            
          
                
          正規化とハッシュチェーン
          
                
          各ブロックの hash
                    は、ファイル先頭からそのブロックの開始行の直前までのバイト列（スライス）を正規化して計算します。後続の署名者は先行するブロックも含めて署名するため、署名は追記専用のチェーンを形成します。
          
            
          
            
          
                
          
                    
          正規化 normalize(S)
          
                    
            
                        
          1. 先頭の UTF-8 BOM（EF BB BF）を除去する。
            2. 
                        
          2. CRLF を LF に置換し、残った CR
                            も LF に置換する。
            3. 
                        
          3. 末尾の LF・SP・HTAB
                            をすべて除去する。
            4. 
                        
          4. LF をちょうど1つ付加する。
            5. 
                    
          
                    
          Unicode 正規化は行わないため、NFC と NFD
                        は別の文書として扱われます。これ以外のバイトを変更すると、文書内部の空白であっても署名は破壊されます。文書は有効な UTF-8 であることが必要です。
          
                    
          チェーンの検出
          
                    
            
                        
          1. ファイル末尾から走査し、末尾の空白は無視する。
            2. 
                        
          2. 最終行が --> であれば、直前の
                            <!-- md-signature までを1つのブロックとして読む（間の行がすべて有効なフィールド行の場合）。ブロック間の空白行を読み飛ばして繰り返す。
                        
            3. 
                        
          3. ブロックでも空白でもないテキストに到達した時点で停止する。そこまでが本文。
            4. 
                    
          
                    
          
                        本文中のブロック（後ろに文章が続くコード例など）はチェーンに含まれず、検証されません。最後のブロックの後に空白以外のテキストがある場合、そのテキストはどの署名の対象でもないため、検証は失敗します。生成者も、この状態の文書への連署を拒否します。
                    
          
                
          
                
          
                    
                
          
            
          
            
          仕様書 §5.1 文書の正規化、§5.2
                        チェーンと文書スライス
          
        
          

        
          
            
          
                
          署名対象ペイロード
          
                
          秘密鍵で署名する対象は、ブロックのフィールドから組み立てた短いテキストです。このテキストに hash
                    が含まれるため、1つの署名で文書本体とメタデータの両方を保護します。
          
            
          
            
          
                
          
                    
          組み立て手順
          
                    
            
                        
          1. フィールドから
                            sig、tsa_url、tsa_token、webauthn_authenticator_data、webauthn_client_data
                            を除外する。
            2. 
                        
          2. キーを ASCII バイト列として比較し、昇順に整列する。
            3. 
                        
          3. 各フィールドを key=value として出力する。値内の LF
                            は LF と2スペースとして出力する。キーは英小文字で始まるため、継続行が別のフィールドと誤認されることはない。
            4. 
                        
          4. LF で連結し（末尾に LF は付けない）、先頭に
                            md-signature/v1 と LF を付加する。
            5. 
                        
          5. UTF-8
                            でエンコードし、sig = "base64:" + base64(Sign(private-key, payload)) を計算する。
            6. 
                    
          
                    
          この設計の帰結
          
                    
            
                        
          • 
                            signer・role・reason・ts
                            もペイロードに含まれるため、いずれかを変更すると署名は破壊されます。
            • 
                        
          • tsa_url と tsa_token
                            はペイロード外なので、タイムスタンプは署名後に追加できます。
            • 
                        
          • 先頭行 md-signature/v1
                            はドメイン分離用です。git-hosting は SSH 認証用の鍵を再利用するため、この行によって SSH 認証データや他プロトコルの署名対象と区別します。

          仕様書 §5.3
                        ダイジェストと署名対象ペイロード
          
        
          

        
          
            
          
                
          公開鍵の解決
          
                
          method
                    は、検証者が公開鍵を取得する場所を指定します。有効な署名が示すのは「解決した鍵の保持者が、このバイト列に署名した」という事実です。その鍵が誰に結び付くかは方式によって異なります。
          
            
          
            
          
                
          
                    
          
                        
                            
          
                                方式
                                鍵の取得先
                                結び付く対象
                            
          
                                  
                        
                            
          
                                dns
                                selector があれば
                                    <selector>._mdsig.<signer>、なければ
                                    _mdsig.<signer> の TXT レコード。値は
                                    v=mdsig1; k=ed25519; p=<base64>。レコードが複数あれば、いずれかで検証できれば有効（鍵のローテーション用）。ブラウザなどシステムのリゾルバを使用できない環境では
                                    DNS-over-HTTPS で取得する。
                                ドメインの運用者
                            
          
                            
          
                                git-hosting
                                
                                    https://<signer>.keys（例：https://github.com/alice.keys）の
                                    ssh-ed25519
                                    行。key_fp（SHA256:…）があればその鍵のみを使用する。sig
                                    はペイロードに対する生の Ed25519 署名で、ssh-keygen -Y sign の SSHSIG 形式は使用しない。
                                Git ホスティングサービスのアカウント
                            
          
                            
          
                                tofu
                                ブロック内の
                                    pubkey: ed25519:<base64>。状態を保持する検証者は signer と
                                    pubkey の対応を記録し、同じ signer の鍵が変化すれば警告する。
                                鍵そのもののみ。署名後に改変されていないことは示すが、署名者が誰であるかは示さない。
                            
          
                            
          
                                pgp
                                fpr
                                    の鍵を、ローカルの鍵束、signer のドメインの WKD、検証者が設定した鍵サーバ（既定は
                                    keys.openpgp.org）の順に検索する。鍵サーバは署名ブロックでは指定できない。署名は gpg でも作成できるため、スマートカード上の鍵も使用できる。
                                
                                メールアドレス（WKD ではドメインの運用者、keys.openpgp.org では確認済みのアドレス）
                            
          
                                  
                    
          
                    
          dns、git-hosting、pgp（WKD・鍵サーバ）
                        は検証時点の鍵を取得します。署名者が鍵を削除すると古い署名は検証できなくなり、ドメインやアカウントが乗っ取られると攻撃者の鍵が公開されます。どちらも文書だけでは検出できないため、長期の証拠には
                        RFC 3161 タイムスタンプの付与が推奨されています。
          
                
          
                
          
                    
          パスキー（alg: webauthn-es256）
          
                    
          認証器は任意のデータには署名しません。生成者は
                        challenge = SHA-256(payload) と rpId = rp_id を指定して
                        navigator.credentials.get() を呼び出し、応答を3つのフィールドに格納します。公開鍵は
                        tofu（pubkey: es256:…）または
                        dns（k=es256）から取得します。
          
                    
          challenge = SHA-256(payload)
signed    = authenticatorData || SHA-256(clientDataJSON)
sig       = "base64:" DER(ECDSA-P256-SHA256(signed))
          
                    
          検証者の確認事項
          
                    
            
                        
          1. clientDataJSON の type が
                            webauthn.get で、challenge が SHA-256(payload) の
                            base64url と一致する。
            2. 
                        
          2. origin のホストが rp_id
                            またはそのサブドメインで、localhost 以外は https である。
            3. 
                        
          3. authenticatorData の先頭32バイトが
                            SHA-256(rp_id) と等しく、User Present フラグが立っている。
            4. 
                        
          4. 上の式の signed に対する ECDSA P-256 / SHA-256 署名が、候補の
                            es256 鍵で検証できる。
            5. 
                    
          
                
          
            
          
            
          仕様書 §4 公開鍵の解決方法
          
        
          

        
          
            
          
                
          検証手順と結果
          
                
          検証者はチェーンの各ブロックを順に検査し、ブロックごとにステータスを決定します。文書全体が検証済みとなるのは、すべてのブロックが valid
                    の場合に限られます。
          
            
          
            
          
                
          
                    
          ブロックごとの手順
          
                    
            
                        
          1. ブロックを解析する。構文エラー、必須フィールドの欠落、未知のフィールドがあれば malformed
            2. 
                        
          2. スライス（scope
                                指定時はセクション）のダイジェストを計算し、hash と比較する。不一致なら invalid · hash-mismatch
            3. 
                        
          3. ペイロードを構築し、method で候補鍵を解決する。ネットワーク起因の失敗は
                                invalid と区別して unresolved
            4. 
                        
          4. 各候補鍵で sig を検証する。どの鍵でも成立しなければ
                            invalid · bad-signature
            5. 
                        
          5. expires を過ぎていれば invalid · expired
            6. 
                        
          6. resources、revocation_url、tsa_token
                                があれば、それぞれ検査する。
            7. 
                    
          
                    
          文書が verified
                        となる条件は、チェーンにブロックが1つ以上あり、すべてが valid で、最後のブロックの後に未署名の内容がないことです。require が満たされていなければ
                        verified but pending となり、検証者はこれを完了として提示してはなりません。
          
                    
          
                        
          合意ステータス
          
                        
          
                            
          
                                
          none
          
                                
          要件なし
          
                            
          
                            
          
                                
          complete
          
                                
          すべて充足
          
                            
          
                            
          
                                
          pending
          
                                
          不足あり（不足する連署を列挙）
          
                            
          
                        
          
                    
          
                
          
                
          
                    
          ステータス
          
                    
          
                        
                            
          
                                status
                                意味
                                主な code
                            
          
                                  
                        
                            
          
                                valid
                                すべての検査に合格した。
                                null
                            
          
                            
          
                                invalid
                                改ざん、期限切れ、撤回など。
                                hash-mismatch bad-signature
                                    expired revoked scope-missing
                                    resource-mismatch resource-missing
                            
          
                            
          
                                malformed
                                ブロックとして解釈できない。
                                malformed unknown-field
                            
          
                            
          
                                unresolved
                                鍵やリソースを取得できず、判定できない。
                                network not-found offline
                            
          
                            
          
                                unsupported
                                未対応の版・アルゴリズム・方式。有効とは報告しない。
                                unsupported-version unsupported-alg
                                    unsupported-hash unsupported-method
                            
          
                                  
                    
          
                    
          mdsig verify の終了コード
          
                    
          
                        
                            
          
                                0
                                すべての署名が有効（--offline で未検査のものを含む）
                            
          
                            
          
                                1
                                検証失敗：ハッシュ不一致、不正な署名、形式不正、未対応、署名なし、末尾の未署名内容など
                            
          
                            
          
                                2
                                使い方の誤り：未知のフラグ、引数の欠落、無効なフィールド値
                            
          
                            
          
                                3
                                ネットワークまたは鍵解決のエラー（終了コード 1 となる失敗がない場合）
                            
          
                            
          
                                4
                                ファイル I/O またはパーミッションのエラー
                            
          
                            
          
                                5
                                すべての署名は有効だが、require
                                    の連署が不足（pending）
                            
          
                                  
                    
          
                    
          複数ファイルの場合は最も重大なコードを返します（1 > 4 > 3 >
                        5 > 0）。
          
                
          
            
          
            
          仕様書 §5.4 検証手順CLI 仕様 §4
                        終了コード
          
        
          

        
          
            
          
                
          拡張フィールド
          
                
          v0.0.1 は、基本のフィールドに加えて次の任意フィールドを規定します。tsa_url と
                    tsa_token 以外は署名対象ペイロードに含まれるため、署名後に変更すると署名が破壊されます。
          
            
          
            
          
                
                    
          
                        フィールド
                        用途
                        例
                    
          
                          
                
                    
          
                        scope
                        
                            マーカーで囲んだセクションのみに署名し、それ以外の部分は署名後も編集できる。ハッシュの入力は、列挙順に連結した各セクションの
                            normalize(section)。検証者は部分署名であることを必ず表示する。ID が見つからなければ
                            invalid（scope-missing）。
                        
                            
          scope: section:terms,section:fees

<!-- mdsig:section terms -->
## Terms
<!-- /mdsig:section -->
          
                                  		
                    
          
                    
          
                        require
                        文書の完了に必要な後続の連署を宣言する。後続の有効なブロックと
                            method・signer（指定時は role も）で照合し、不足があれば合意ステータスは
                            pending（CLI の終了コード 5）。
                        
                            
          require: |
  dns:example.com approver
  git-hosting:github.com/bob
          
                                  		
                    
          
                    
          
                        resources
                        参照する画像などのファイルや URL を SHA-256
                            で固定する。ローカルの相対パスは常に検査する。https:// の URL は、取得すると検証の事実が配信元に伝わるため、利用者が要求した場合のみ取得する。
                        
                        
                            
          resources: |
  sha256:e3b0c442…b855 ./diagram.png
  sha256:8f434346…7aa4 https://example.com/chart.png
          
                                  		
                    
          
                    
          
                        expires
                        署名の有効期限。検証者の時計で期限を過ぎていれば
                            invalid（expired）。実在しない日時は malformed。
                        
                            
          expires: 2027-03-31T23:59:59Z
          
                                  		
                    
          
                    
          
                        revocation_url
                        署名者の撤回リストの https:// URL。リスト自体も
                            md-signature 文書で、同じ method・signer
                            の有効な署名を持つ場合のみ信頼する。取得できない場合は「撤回未検査」と報告し、それだけでは無効にしない。
                        
                            
          revocation_url: https://example.com/.well-known/mdsig-revoked.md
# list body
revoked: sha256:<hex of SHA-256(signed payload)>
          
                                  		
                    
          
                    
          
                        tsa_url tsa_token
                        RFC 3161 タイムスタンプ。messageImprint は
                            SHA-256(sig の生バイト列)。ts
                            と異なり、署名がその時刻に存在したことの第三者による証拠になる。検証者は応答ステータスと imprint を確認する。
                        
                            
          tsa_url: http://ts.ssl.com
tsa_token: |
  gzip+base64:H4sIAAAAAAAA/+3SW0hTURwG8G+m…
          
                                  		
                    
          
                          
            
          
            
          alg は ed25519
                が実装必須、webauthn-es256
                は検証の実装を推奨。ml-dsa-44・ml-dsa-65・slh-dsa-sha2-128s・ed25519+ml-dsa-65
                は予約済みで、未対応のアルゴリズムは unsupported と報告されます。
