公開鍵の解決

method は、検証者が公開鍵を取得する場所を指定します。有効な署名が示すのは「解決した鍵の保持者が、このバイト列に署名した」という事実です。その鍵が誰に結び付くかは方式によって異なります。

方式と鍵の取得先

方式 鍵の取得先 結び付く対象
dns selector があれば <selector>._mdsig.<signer>、なければ _mdsig.<signer> の TXT レコード。値は v=mdsig1; k=ed25519; p=<base64>。レコードが複数あれば、いずれかで検証できれば有効（鍵のローテーション用）。ブラウザなどシステムのリゾルバを使用できない環境では DNS-over-HTTPS で取得する。 ドメインの運用者
git-hosting https://<signer>.keys（例：https://github.com/alice.keys）の ssh-ed25519 行。key_fp（SHA256:…）があればその鍵のみを使用する。sig はペイロードに対する生の Ed25519 署名で、ssh-keygen -Y sign の SSHSIG 形式は使用しない。 Git ホスティングサービスのアカウント
tofu ブロック内の pubkey: ed25519:<base64>。状態を保持する検証者は signer と pubkey の対応を記録し、同じ signer の鍵が変化すれば、利用者が新しい鍵を承認するまで invalid（key-changed）とする。鍵はデコードしたバイト列で比較する。 鍵そのもののみ。署名後に改変されていないことは示すが、署名者が誰であるかは示さない。
pgp fpr の鍵を、ローカルの鍵束、signer のドメインの WKD、検証者が設定した鍵サーバ（例：keys.openpgp.org）の順に取得を試みる。鍵サーバは署名ブロックでは指定できない。署名は gpg でも作成できるため、スマートカード上の鍵も使用できる。 メールアドレス（WKD ではドメインの運用者、keys.openpgp.org では確認済みのアドレス）
directory signer のドメインの _mdsig TXT レコードの dir= が指すディレクトリ、なければ検証者が信頼するディレクトリの一覧（既定は https://keys.mdsig.dev）に GET <dir>/v1/keys/<sha256(signer)> で問い合わせる。ディレクトリはブロックでは指定できない。 メールアドレス（ドメインの dir で選択した場合はドメインの運用者、一覧から選択した場合はディレクトリによるアドレスの確認）

dns、git-hosting、directory、pgp（WKD・鍵サーバ）は検証時点の鍵を取得します。署名者が鍵を削除すると古い署名は検証できなくなり、ドメインやアカウントが乗っ取られると攻撃者の鍵が公開されます。どちらも文書だけでは検出できないため、長期の証拠には tsa ブロックと公開鍵のスナップショットを併用します（「長期保存」を参照）。

パスキー（alg: webauthn-es256）

認証器は任意のデータには署名しません。生成者は challenge = SHA-256(payload) と rpId = rp_id を指定して navigator.credentials.get() を呼び出し、応答を3つのフィールドに格納します。公開鍵は tofu（pubkey: es256:…）、dns（k=es256）、directory から取得します。

challenge = SHA-256(payload)
signed    = authenticatorData || SHA-256(clientDataJSON)
sig       = "base64:" DER(ECDSA-P256-SHA256(signed))

検証者の確認事項

  1. clientDataJSON の type が webauthn.get で、challenge が SHA-256(payload) の base64url と一致する。
  2. origin のホストが rp_id またはそのサブドメインで、localhost 以外は https である。
  3. clientDataJSON の crossOrigin が true でない。別のオリジンに埋め込まれたフレームで作成されたアサーションは拒否する。
  4. authenticatorData の先頭32バイトが SHA-256(rp_id) と等しく、User Present フラグが立っている。
  5. 上の式の signed に対する ECDSA P-256 / SHA-256 署名が、候補の es256 鍵で検証できる。

User Verified（UV）フラグは署名の有効性に影響しませんが、require の user_verified の判定に使用します。検証者は UV と、同期されたパスキーか（BE／BS）を報告します。

仕様書 §4 公開鍵の解決方法

識別子の正規化

署名者の識別子（method:signer）は、require、名簿、撤回リストとの照合に使用します。照合は完全一致で行うため、signer は方式ごとに決まった正規の形で書きます。正規の形でない値のブロックは malformed です。

方式 正規の形
dns ASCII の小文字・数字・ハイフンからなるドメイン名。2ラベル以上、末尾のドットなし、最後のラベルは数字だけにしない。国際化ドメイン名は xn-- の A-label で書く。
git-hosting <host>/<username>。ホストは上と同じドメイン名（IP アドレスや localhost は不可）、利用者名は小文字。
pgp directory local@domain。ローカル部に ASCII の英大文字を含めず、ドメインは上と同じ形。引用符で囲んだローカル部は不可。
tofu 空白と * を含まない任意の文字列。大文字小文字を含め、書かれたとおりに比較する。

比較と表示

  • 大文字小文字の同一視や末尾のドットの除去は行いません。CLI は tofu 以外の --signer の英大文字を小文字に変換して書き込みます。
  • signer に * は使えません。* は require のパターン専用です。
  • pubkey は、base64 をデコードした鍵のバイト列で比較します。生の鍵と SPKI 形式は同じ鍵として扱います。
  • 照合は構文の検査だけで行います。表示する際は、IDNA2008 の検証に通り単一の文字体系からなる A-label に限り、U-label（例：日本語のドメイン名）を示してかまいません。
signer: xn--r8jz45g.example     # ok
signer: Example.com              # malformed
signer: example.com.             # malformed
signer: github.com/Alice         # malformed

仕様書 §3.4 識別子の正規化

公開鍵の公開手順

検証者が鍵を取得できるよう、署名の前に方式ごとの公開先へ鍵を登録します。CLI の mdsig keygen は Ed25519 の鍵ペアと、DNS に登録する TXT レコードを出力します。

dns、git-hosting、directory の署名では、署名に用いた鍵をブロックに埋め込めます（--embed-key。directory は既定で埋め込み、--no-embed-key で省略）。鍵を削除した後も、その鍵で署名が成立することを確認できます。詳しくは「長期保存」の「公開鍵のスナップショット」を参照してください。
