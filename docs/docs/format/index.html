形式と署名の計算

署名ブロックの書式、ハッシュの対象となる範囲、秘密鍵が署名するバイト列を順に説明します。別の言語で実装する場合は、このページと検証手順のページが出発点になります。

署名ブロックの形式

署名ブロックは、<!-- md-signature の行で開始し --> の行で終了する HTML コメントです。内部には key: value 形式のフィールドを1行に1つずつ記述し、文書の末尾に配置します。

キー 要否 内容
v 必須 形式のバージョン。本版は 0.1 のみを定義する。0.0.x のブロックは unsupported（unsupported-version）。
method 必須 公開鍵の解決方法。dns・git-hosting・pgp・tofu・directory のいずれか。タイムスタンプブロックは tsa。
signer 必須 署名者の識別子。構文は method に依存する（github.com/alice、example.com など）。ASCII の英字は小文字の正規の形で書き、比較は完全一致。
ts 必須 署名者が申告する署名時刻（UTC、YYYY-MM-DDTHH:MM:SSZ）。申告値にすぎず、第三者の証拠にはならない。
hash 必須 対象スライスのダイジェスト。<hash-alg>: に続けて小文字の16進数。sha256（tsa ブロックは sha512 も使用できる）。
sig 必須 署名対象ペイロードに対する署名。base64: に続けてパディング付きの標準 base64。
alg 必須 署名アルゴリズム。ed25519・webauthn-es256・openpgp・rfc3161 など。省略時の既定はない。
display_name 任意 署名欄に示す表示名。64 コードポイントまでの自己申告で、検証済みの signer と並べて「申告」として表示する。
role reason 任意 役割は [a-z0-9][a-z0-9._-]* の単一の語（推奨値は author・reviewer・approver・witness）。理由は自由記述。
selector key_fp pubkey fpr 条件付き 方式ごとの鍵情報（「公開鍵の解決」で説明）。
rp_id webauthn_* 条件付き alg が webauthn-es256 の場合は必須、それ以外の場合は記述不可。
expires scope require resources revocation_url 任意 期限・部分署名・リソース・撤回（「拡張フィールド」）、必須の連署（「連署ワークフロー」）。時刻の証拠は別の tsa ブロックで示す（「長期保存」）。
x_* 任意 私的利用の拡張。意味は規定されないが、署名対象ペイロードに含まれる。

構文規則

  1. 開始行は <!-- md-signature、終了行は --> のみで構成する。フィールドの順序は任意で、同じキーの重複は malformed。
  2. 空行を含めない。CommonMark は空行で HTML ブロックを終了するため、以降の行が表示されてしまう。
  3. 値に -->、--!>、<!-- を含めない。コメントが途中で終了し、可視の Markdown を注入される原因になる。-- だけなら使用できるため、xn-- で始まる国際化ドメイン名も署名者にできる。生成者はこの入力を修正せず拒否する。
  4. key: | と2スペース字下げの継続行で折り返し値となり、各行を LF で連結する。2スペースより後の空白は値の一部で、継続行の末尾の空白は malformed。リストと、76文字を超えるバイナリ値に使用する。
  5. 本書で未定義のキーは malformed（unknown-field）。x_ で始まるキーのみ例外。将来の拡張を解釈しない検証者による誤判定を防止する。
  6. 制御文字、書式文字（双方向制御文字、ゼロ幅文字など）、U+2028／U+2029、非文字を値に含めない。検証結果の表示の偽装に使用できるため。
  7. YAML に似ているが YAML ではない。値はすべて文字列で、YAML のパーサで読み書きすると v: 0.1 が数値になるなどして署名が壊れる。

仕様書 §3 署名ブロックの構文

正規化とハッシュチェーン

各ブロックの hash は、ファイル先頭からそのブロックの開始行の直前までのバイト列（スライス）を正規化して計算します。後続の署名者は先行するブロックも含めて署名するため、署名は追記専用のチェーンを形成します。

正規化 normalize(S)

  1. 先頭の UTF-8 BOM（EF BB BF）を除去する。
  2. CRLF を LF に置換し、残った CR も LF に置換する。
  3. 末尾の LF・SP・HTAB をすべて除去する。
  4. LF をちょうど1つ付加する。

Unicode 正規化は行わないため、NFC と NFD は別の文書として扱われます。これ以外のバイトを変更すると、文書内部の空白であっても署名は破壊されます。文書は有効な UTF-8 であることが必要です。

チェーンの検出

  1. ファイル末尾から走査し、末尾の空白は無視する。
  2. 最終行が --> であれば、直前の <!-- md-signature までを1つのブロックとして読む（間の行がすべて有効なフィールド行の場合）。ブロック間の空白行を読み飛ばして繰り返す。
  3. ブロックでも空白でもないテキストに到達した時点で停止する。そこまでが本文。

本文中のブロック（後ろに文章が続くコード例など）はチェーンに含まれず、検証されません。最後のブロックの後に空白以外のテキストがある場合、そのテキストはどの署名の対象でもないため、検証は失敗します。生成者も、この状態の文書への連署を拒否します。

仕様書 §5.1 文書の正規化、§5.2 チェーンと文書スライス

署名対象ペイロード

秘密鍵で署名する対象は、ブロックのフィールドから組み立てた短いテキストです。このテキストに hash が含まれるため、1つの署名で文書本体とメタデータの両方を保護します。

組み立て手順

  1. フィールドから sig、webauthn_authenticator_data、webauthn_client_data を除外する。
  2. キーを ASCII バイト列として比較し、昇順に整列する。
  3. 各フィールドを key=value として出力する。値内の LF は LF と2スペースとして出力する。キーは英小文字で始まるため、継続行が別のフィールドと誤認されることはない。
  4. LF で連結し（末尾に LF は付けない）、先頭に md-signature/v1 と LF を付加する。
  5. UTF-8 でエンコードし、sig = "base64:" + base64(Sign(private-key, payload)) を計算する。

この設計の帰結

  • signer・role・reason・ts もペイロードに含まれるため、いずれかを変更すると署名は破壊されます。
  • 署名対象外のフィールドは sig と webauthn_* だけです。時刻の証拠は、署名済みのブロックを変更せず、後ろに tsa ブロックを追記して付与します。
  • 先頭行 md-signature/v1 はドメイン分離用です。git-hosting は SSH 認証用の鍵を再利用するため、この行によって SSH 認証データや他プロトコルの署名対象と区別します。
