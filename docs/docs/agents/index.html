エージェント間の合意記録

AI エージェントが人に代わって購入や契約の承諾を行う場面で、Markdown で書いた取引条件への署名と連署を md-signature で記録する方法です。支払い、委任、責任分担は隣接するプロトコルに任せ、条件文書への同意の部分だけを担います。このページは参考情報で、規範は仕様書です。

役割分担

以下のプロトコルはいずれも策定中で、フィールド名や構造は変わりえます。実装する際は各プロトコルの最新の仕様に従ってください。

プロトコル 扱う範囲 md-signature との関係
LCP 条件文書の所在（/.well-known/legal-context.json の terms）と、その SHA-256（atrHash）の公開。署名を信頼の段階として定めるが、署名の方式は規定しない。 条件文書そのものと、署名・連署の形式を提供する。atrHash は承諾ブロックの hash と一致させられる。
x402 HTTP 402 による支払いの要求と決済。支払いの要求（accepts[]）に追加の情報（extra）を載せられる。 支払いの要求に atrHash を載せ、どの条件に対する支払いかを結び付ける。
AP2 利用者がエージェントに与える委任（マンデート）と、その検証。 代理権の証明は AP2 に任せる。md-signature の署名が示すのは「その鍵の保持者が条件に同意した」ことだけ。
PACT エージェント間の契約における責任と決済（保証金、エスクロー、下請けの連鎖）。 責任と決済は PACT に任せ、条件文書への同意の記録として併用する。

参照日：2026-11-27（LCP は Specification v1.0 の草案、PACT は draft-laxsharma-pact-01）。

全体の流れ

  1. 提供者（売り手のエージェント）が取引条件を Markdown で書き、dns 方式で署名する。require で、承諾に必要な連署と自身の最終確認を宣言する。
  2. 提供者は署名済みの文書を正規化した形（LF、BOM なし、末尾の改行1つ）で公開し、LCP の terms に URL を、atrHash に SHA-256 を記載する。
  3. 承諾者（買い手のエージェント）は文書を取得し、SHA-256 を atrHash と照合して検証する。次に必要な連署は next で分かる。
  4. 承諾者は、自身の承認条件（人の承認が必要かなど）を自分のブロックで宣言しつつ連署する。
  5. 承諾者側の承認者が連署し、最後に提供者が最終確認の連署をすると、合意ステータスが complete になる。
  6. 支払いは x402 などで行う。支払いの要求に atrHash を載せると、どの条件に対する支払いかを特定できる。

承認条件の宣言と最終確認

承認条件は、各当事者が自分のブロックで宣言します。提供者は承諾の受け方を、承諾者は自社の承認の手順を書きます。相手の文書に書かれた条件に従う義務はなく、全員の宣言が満たされたときに complete になります。

承諾者のエージェントが承諾した後、buyer.example の DNS の名簿に載る社員がパスキーで承認し、最後に提供者が最終確認をすると完了します。

最終確認の型（推奨）

  • dns:* のようなパターンで誰でも承諾できる申込は、複製されて別々に成立しえます。第三者が先に署名して席を埋めることもできます。
  • 名簿やパターンは相手の資格の確認に使い、締結の確定は、最後の段階で提供者自身を名指しした最終確認で行います。提供者は最終確認の前に、在庫、価格、取引の重複を確認します。
  • 最終確認は名指しの行なので自己承諾の防止の対象外で、提供者は同じ識別子で、別のブロックとして署名できます。
  • パターンを含む宣言には order mode=strict を書けないため、順序は既定の pending とします。
  1. #1dns:shop.exampleofferor · require
  2. #2dns:buyer.exampleacceptor · require
  3. #3directory:carol@buyer.exampleapprover · user_verified
  4. #4dns:shop.exampleconfirm

#2 は提供者の段階1を、#3 は承諾者の宣言を、#4 は提供者の段階2を満たします。

エージェントの鍵と期限

  • エージェントの鍵は、組織のドメインの dns 方式で、エージェントごとのセレクタを使って公開します。廃止する際はレコードを削除し、それまでの署名に備えて鍵のスナップショット（pubkey）と tsa ブロックを付けておきます。
  • 署名が示すのは、そのドメインが公開した鍵の保持者が条件に同意したことまでです。エージェントが誰の代理として、どの範囲で行動できるかは、AP2 のマンデートなどで示します。
  • 人の承認が必要な場合は、その人のパスキーによる連署を user_verified で要求します。
agent-checkout._mdsig.shop.example. IN TXT "v=mdsig1; k=ed25519; p=11qY…URo="
agent-procure._mdsig.buyer.example.  IN TXT "v=mdsig1; k=ed25519; p=PUAX…Zgw="

申込の期限と改訂

  • 申込の期限に expires を使ってはいけません。期限を過ぎるとブロックは無効になり、期限内に成立した契約まで、後から検証すると無効に見えます。期限は本文に書き、提供者が最終確認の段階で、承諾が期限内か（T(k)）を判断します。機械的な判定は将来の版で扱う予定です。
  • 条件を改訂する場合は新しい版の文書を作り、前の版を resources で参照します。どの版を改訂したかが署名で固定されます。前の版の署名を取り消すには撤回リストを使います。
resources: |
  https://shop.example/terms/v2.md hash=sha256:9f2c…e1

取引条件の書き方と相手の文書の扱い

  • 金額、数量、納期などは、LCP の構造化フィールド、または本文中のコードフェンス（情報文字列 json など）に書きます。構造化された条件と本文の文章が食い違う場合は本文の文章が優先することを、本文に明記します。
  • 取引 ID と相手方（相手の識別子、または資格の条件）を本文に書きます。署名は本文を対象とするため、同じ条件文書を別の取引に流用されることを防げます。
  • 表示に影響する HTML（コメント、隠し要素）を条件に使いません。

相手から受け取った条件文書は、信頼できない入力として扱います。エージェントは本文の指示（「承諾したら次の URL に支払え」など）に従ってはなりません。検証の結果（署名者、合意ステータス、next）と自身の方針だけに基づいて判断します。
