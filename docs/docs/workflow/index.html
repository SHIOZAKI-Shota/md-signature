連署ワークフロー

署名者は、文書の完了に必要な連署を require に宣言できます。宣言は署名対象ペイロードに含まれるため、後続の署名者が書き換えることはできません。誰を名指しするか、どの組織の誰でもよいか、何人そろえばよいか、どの順番で署名するかを書けます。検証者は宣言と後続の署名を照合し、合意の状態と次に必要な連署を報告します。

require の宣言

require は折り返し値で、1行に1つずつ次の3種類の行を記述します。段階行を用いない場合、すべての要件行が1つの段階となり、全員の署名を必要とします。字下げは読みやすさのためだけのもので、構造は持ちません。

行の種類 構文 意味
順序行 order mode=<m> 順番より前に署名した場合の扱い。pending、guide、strict のいずれかで、最初の行にのみ記述できる。省略時は pending。
段階行 step [any=<m>] 以降の要件行が属する段階を開始する。段階には現れた順に 1 から番号が付く。any=m は、その段階で異なる m 者の署名がそろえば成立することを示す。省略時は全行。
要件行 <method>:<signer> [attr…] 必要な署名者（対象）と、その署名が満たすべき条件（属性）。対象には名指しの識別子か、パターン（dns:* など）を書く。

形式不正（malformed）となる値

  1. ABNF に一致しない。順序行が最初の行以外にある、段階行より前に要件行がある、要件行のない段階がある、など。
  2. 要件行の方式が tsa である。名指しの識別子が正規の形でない（大文字を含む、末尾のドットがあるなど）。
  3. * を含む対象が、パターンの一覧にない（dns:ex*.com、tofu:* など）。
  4. 属性が使えない行に付いている、値の構文が誤っている、または同じ属性が重複している。
  5. パターンの行がない段階で、any=m の m が名指しされた異なる署名者の数を超える。any のない段階に、同じ署名者しか満たせない行が2つ以上ある。
  6. order mode=strict の宣言がパターンの行を含む。

本書が定義しない方式（foo:bar）や属性は形式不正にはせず、合意ステータスを unsupported とします。署名そのものは有効なままです。

属性とパターン

要件行は「対象 → 属性」の形です。ブロックが行を満たすのは、署名者の識別子が対象に一致し、かつすべての属性を満たす場合です。属性は 名前=値 または値のない 名前 で、空白1つで区切ります。

属性 使える行 意味
role=<word> すべての方式 ブロックの role が値と完全に一致する。role は署名者自身の申告にすぎないため、照合の根拠は署名者の識別子にある。
user_verified dns、directory、pubkey= を持つ tofu alg: webauthn-es256 の有効なブロックで、認証器が利用者確認（UV）と利用者の存在（UP）を示している。パスキーで本人が操作した署名を求める場合に使う。
member_of=<roster> パターンの行と名指しの行（tofu を除く） 署名者が名簿に載っている。名簿は dns:<domain>（DNS の名簿）または https:// の URL（署名済みの名簿）。
pubkey=<type>:<b64> tofu の名指しの行のみ ブロックの pubkey が同じ鍵である。鍵はデコードしたバイト列で比較する。

tofu では誰でも同じ名前の鍵を作成できるため、tofu の要件行には pubkey= を付けることを推奨します。付けない場合、検証者は「自称の名前で誰でも満たせる要件」と警告します。tofu の行の user_verified には pubkey= が必須です。

パターン 一致する署名者
dns:* すべての dns の署名者
dns:*.example.com example.com の下位のドメイン（a.example.com、a.b.example.com）。example.com 自身と badexample.com は含まない
directory:*@example.com
pgp:*@example.com		 ドメイン部分が example.com と完全に一致するメールアドレス。sales.example.com のアドレスは含まない
directory:* pgp:*
git-hosting:*		 その方式のすべての署名者。git-hosting にはホストを限定するパターンはない

一覧は閉じており、これ以外で * を含む対象は malformed です。tofu と tsa のパターンはありません。パターンが限定するのは方式とドメインだけで、相手の適格性は判断しません。資格を限定するには member_of を併用します。パターンの行は、宣言したブロックと同じ署名者を数えません（自己承諾の防止）。

属性とパターンの一覧は 記法の早見表 にもまとめています。

組織の指定

「ある組織の誰か」の署名を求める場合は、次の順に手段を検討します。メールアドレスのドメインを持つことは、その組織に所属していることを示すとは限りません。

  1. 組織の構成員を求める場合は、DNS の名簿を推奨します。組織の DNS を管理する者が、構成員の識別子を1件ずつ TXT レコードで公開します。member_of=dns:example.com。
  2. 業界団体の会員のように第三者が認定する資格には、署名済みの名簿を使用します。その第三者が、会員の一覧を md-signature 文書として公開し、自身のドメインで署名します。member_of=https://assoc.example/members.md。
  3. 名簿を用意できない場合は、directory:*@example.com のようにドメインのパターンだけで限定することもできます。

名簿の判定

  • 名簿は検証の時点の内容で判断します。構成員の追加や削除によって、同じ文書の合意の状態が後から変わることがあります。保存を目的とする検証者は、使用した名簿の SHA-256 を記録します。
  • オフラインの場合、名簿を取得できない場合、DNS の問い合わせが SERVFAIL やタイムアウトになった場合は、その行は判定不能となり、合意ステータスは undetermined（終了コード 3）になります。NXDOMAIN と NODATA は「名簿に載っていない」です。
  • https の名簿の発行者は、書かれた URL のホストを署名者とする dns:<host> です。リダイレクト先のホストではありません。発行者の有効な署名（scope なし）がない名簿は信頼しません。

段階の数え方

要件は、宣言したブロックより後ろにある有効なブロックと照合します。照合に用いるのは、署名によって認証される署名者の識別子（method:signer）で、比較は完全一致です。

数える規則

  1. 数えるのは、有効で、scope を持たず、tsa でなく、段階の開始位置より後ろにあるブロック。
  2. 各署名者は、1つの段階で1行にのみ数える。「異なる署名者」は識別子の違いで判断するため、同じ組織が別の方式で署名すると別の署名者になる。
  3. any=m の段階は、数えた異なる署名者が m 者に達した時点で成立する。名指しの行は1者、パターンの行は何者でも受け入れる。
  4. どの署名者をどの行に割り当てるかは、仕様の付録 C の手順で一意に決まる。どの実装でも、欠けている連署と next は同じになる。
  5. ある段階で数えたブロックは、同じ宣言の後の段階では数えない。同じ署名者が別のブロックで後の段階を満たすことはできる（最終確認の型）。

要件を満たさないブロック

  • scope を持つブロック。宣言したブロックを署名対象に含まず、同じセクションを持つ別の文書へ移しても有効なままであるため。
  • tsa ブロック。署名者を持たないため。tsa: の要件行も記述できない。
  • invalid、unresolved などのブロック。ただし unresolved のブロックが宣言した要件は収集するため、確認しきれなかったチェーンが完了と報告されることはない。
  • パターンの行に対する、宣言したブロックと同じ署名者のブロック（自己承諾の防止）。別の識別子で署名すれば回避できるため、助言的な防止にとどまる。
  • 宣言したブロックより前にあるブロック。

複数のブロックが require を宣言した場合は宣言ごとに評価し、すべての宣言が成立した時点で complete となります。相手の宣言に従う義務はなく、自分の条件は自分のブロックで宣言します。

順序の扱い（order）

段階のある宣言では、前の段階が成立する前に署名される場合があります。その署名の扱いは、宣言した署名者が順序行 order mode=… で選択します。

mode 順番より前の署名 報告 合意への影響
pending 数えない 数えられなかった署名として、理由 early を付記 その署名者が改めて署名するまで pending
guide 数える 順序違反（violations）として報告。パターンの行にしか一致しない署名は報告しない 影響しない。ほかが満たされれば complete
strict 数える 順序違反（violations）として報告 violated。文書は不合格（終了コード 1）

順序違反と判定するのは、割り当てに入ったブロックだけです。行に一致しただけのブロックは対象外です。step 1 の署名は、宣言したブロックより後ろであれば常に順番どおりです。

strict の宣言にはパターンの行を書けません。パターンに一致する第三者が早く署名するだけで、取り消せない違反を作れるためです。順序そのものに意味がある場合を除き、既定の pending を使います。

合意ステータスと次の連署

検証者は、ブロックごとの判定とは別に、宣言全体の合意ステータスを報告します。成立していない場合は、次に必要な連署（next）と、数えられなかった署名の理由も示します。

status 意味 終了コード
none require の宣言がない 0
complete すべての宣言のすべての段階が成立した 0
pending 成立していない段階がある。欠けている連署（missing）と次の連署（next）を伴う 5
undetermined 通信の失敗、オフライン、名簿を取得できない、評価の上限を超えたなどの理由で判定できない行がある 3
violated order mode=strict の順序違反がある。違反したブロックを列挙する 1
unsupported 検証者が理解しない方式や属性の要件行がある。署名の判定は変えない 1

すべての署名が有効でも、合意が pending または undetermined の文書は verified but pending です。検証者はこれを完了として提示してはなりません。violated と unsupported の文書は合意済みとして提示してはなりません。

数えられなかった理由（rejected）

earlypending の段階の開始位置より前にある
blocked同じ宣言の前の段階で使われた
not-member名簿に載っていない
roster-unavailable名簿による判定ができない
not-user-verifieduser_verified の条件を満たさない
key-mismatchpubkey= の鍵とブロックの鍵が異なる
selfパターンの行で、宣言と同じ署名者
scopedブロックが scope を持つ
unresolvedブロックが未解決（オフラインや通信の失敗で検査できなかった場合を含む）
not-validブロックが有効でも未解決でもない

CLI と CI での利用

mdsig sign の --require は1回につき1行を受け取り、指定した順に行を並べます。段階行の下の要件行は2スペースで字下げして出力します。値全体は署名の前に検査し、形式不正なら終了コード 2 で終了します。

デモとエディタでも、連署の追加画面で同じ宣言を作成できます。

mdsig require explain は、署名の前に宣言を検査し、段階ごとの意味を文章で表示します。tofu の行に pubkey= がない場合などは警告を出します。ライブラリでは explainRequire（TypeScript）と ExplainRequire（Go）で同じ説明を得られます。

連署が不足している間、mdsig verify は終了コード 5 を返すため、このジョブは失敗します。ブランチ保護の必須チェックに設定すれば、全員の署名がそろうまでマージできません。名簿を取得できない間は終了コード 3 です。

エージェントどうしの取引で、資格の確認と最終確認を組み合わせる宣言の例は「エージェント間の合意記録」にあります。
