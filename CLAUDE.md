# md-signature — project context

Repository: https://github.com/SHIOZAKI-Shota/md-signature (website: https://mdsig.dev/ and https://keys.mdsig.dev/, from the separate repository `mdsig_dot_dev`). Go module: `mdsig.dev` (a vanity import path: the website serves `<meta name="go-import">` pointing at the GitHub repository, on the root page, on one page per package path and on `404.html`; go.mod at the repository root; library `…/mdsig`, CLI `…/cmd/mdsig`, so `go install …/cmd/mdsig@latest` installs a binary named `mdsig`).

Open, vendor-neutral format for signing Markdown documents. Signatures are HTML
comments (`<!-- md-signature ... -->`) appended to the end of the file and form an
append-only hash chain. Target: an IETF Internet-Draft (`draft-shiozaki-md-signature-00`, an individual submission; SPEC Appendix A compares it with existing technologies, Appendix B covers formatters).

**Spec documents and which language is authoritative:**
- `SPEC.ja.md` is the **original** (the author writes in Japanese). `SPEC.md` is the **normative** English text kept for a possible IETF submission. Edit the Japanese first, then reflect it in English in the same change, and check that the BCP 14 keyword counts match per section.
- `CLI_SPEC.ja.md` is **normative**; `CLI_SPEC.md` is an informative translation. Keep both in sync in the same change. If code
and spec disagree, fix one of them deliberately; do not let them drift.
- `AGENT_COMMERCE.ja.md` (original) / `AGENT_COMMERCE.md`: informative, no BCP 14 requirements; SPEC cites it as an informative reference. `KEY_DIRECTORIES*.md` are the criteria for the default key-directory list.
- `README*.md`, `packages/core/README*.md` and `CHANGELOG.md` (Japanese) / `CHANGELOG.en.md` are bilingual user docs; change both languages together.

**Versioning:** the format version and the release version are separate. Format `0.1` (the only one verifiers accept); it changes only with incompatible changes (new fields, changed meaning) and becomes `1` when the spec is published as an RFC. Adding registry values (methods, algorithms, hash prefixes, `require` attributes, list types) does not change it. Releases `v0.1.0` (2026-11-27) and `v0.1.1` (2026-11-28) are out and `v0.1.2` is the next tag; the CLI, the Go library and `@mdsig/core` share it (`packages/core/package.json` carries it), `mdsig --version` prints `mdsig version 0.1.2 (format 0.1)`, and the goreleaser release title hard-codes `(format 0.1)` in `.goreleaser.yaml` (change it with the next format bump). 0.0.x documents are `unsupported-version` with a hint to verify them with mdsig v0.0.5 / `@mdsig/core` 0.0.5.

## Principles (do not break)

1. Zero rendering impact: blocks are HTML comments (CommonMark HTML block type 2), no blank lines inside, and no `-->`, `--!>` or `<!--` in values. `--` alone is allowed (IDN A-labels contain it).
2. Single file. No detached signatures.
3. Append-only co-signing: block N signs everything before its open line.
4. Crypto-agility: `alg` / `hash` prefixes; `ed25519` + `sha256` today, PQC names reserved.
5. `packages/core/src` uses **Web-standard APIs only** (Web Crypto, fetch, TextEncoder, CompressionStream). No `node:*`, no `Buffer`, no `process`. Enforced by `npm run check:web-standard`. Tests and scripts may use Node.
6. Licenses: spec docs CC0 1.0 (`LICENSE-SPEC`), code MIT (`LICENSE`).

## Decisions taken beyond the original concept (2026-11-16)

These fill gaps in the initial design handed over from Gemini; all are written into SPEC.md.

- **Chain detection**: the chain is the run of blocks at the very end of the file (whitespace between them only). Blocks elsewhere (e.g. examples in the body) are body content. Text after the last block → verification fails ("unsigned content after the last signature"), and generators refuse to co-sign it without `--force`. Stray-marker detection ignores fenced code blocks.
- **Signed payload** has a domain-separation first line `md-signature/v1` (SSH keys are reused for `git-hosting`).
- **Public key encoding**: Ed25519 keys in `dns` `p=` and `tofu` `pubkey` are raw 32 bytes base64 (DKIM RFC 8463 convention); SPKI DER is accepted.
- **git-hosting** includes `key_fp` (OpenSSH `SHA256:` fingerprint) by default. In browsers, `github.com/<u>.keys` has no CORS, so core falls back to `api.github.com/users/<u>/keys`.
- **Normalization** also strips a leading UTF-8 BOM; documents must be valid UTF-8. Generators preserve the file's CRLF/LF style when appending.
- **Duplicate keys** in a block → malformed. Unknown keys are malformed too (`unknown-field`); only `x_*` keys are free-form and signed.
- **TSA**: timestamps exist only as `tsa` blocks (see Format 0.1). Both implementations verify the token's CMS signature and the TSA certificate chain, and report `genTime` only when that succeeds. The Go CLI uses the system roots plus any `--tsa-root <file>` (verify and sign; `TSAVerifyOptions.ExtraRoots`) (`mdsig/tsa_cms.go`, standard library only; on macOS the roots are read with `/usr/bin/security`, because the platform verifier applies the TLS-server policy). The TS core has no trust store to read, so it carries ten public TSA roots (eight for international public TSAs, plus Security Communication RootCA3 and GlobalSign Timestamping Root R45 for the TSAs accredited by Japan's Minister for Internal Affairs and Communications: Amano chains to SECOM, the others to GlobalSign; their paid services cannot be probed, so only their published TSA certificates were path-validated) (`src/tsa-roots.ts`, generated by `npm run build:tsa-roots` from `packages/core/tsa-roots/*.pem`; never edit it by hand) and accepts `tsaRoots` (verify and sign) to replace them or `extraTsaRoots` to add to them (DER, or PEM text with one or more certificates). Every bundled root is "Included" with the "Time Stamping" EKU in Microsoft's root list on CCADB. The playground uses the built-in list; its "TSA root certificates" section lets a user add roots (PEM/DER, memory only, passed as `extraTsaRoots`; `readTsaRoots` describes them). `.github/workflows/tsa-roots.yml` runs `scripts/update-tsa-roots.ts --write` monthly: it removes roots that left the CCADB list, probes the services in `tsa-roots/services.json`, adds a new root only when CCADB lists its fingerprint for Time Stamping, and opens a pull request (or an issue when it cannot decide). X.509 path validation is in `src/x509.ts`, CMS in `src/tsa-cms.ts`; no policies, no revocation, name constraints rejected. The two trust sets differ, so a token can verify in one implementation and not in the other.
- **pgp** (folded into 0.0.1): `alg: openpgp`, `sig` = one binary OpenPGP signature packet (v4/v6, type 0x00, SHA-256/384/512, hashed issuer fingerprint = `fpr`). Keys: Ed25519 (algo 22/27), RSA ≥ 2048, ECDSA P-256. Lookup: keyring (CLI, `gpg --export`) → WKD → the verifier's keyserver (keys.openpgp.org by default; `mdsig verify --keyserver`, core option `keyserver`). `not-found` only if every source answered "absent", otherwise `network`. Own implementation on Web Crypto in `packages/core/src/pgp-*.ts` (CFB built from one-block AES-CBC); Go uses `github.com/ProtonMail/go-crypto` (BSD-3) for key parsing, fingerprints, signature verification and secret-key unlock, and keeps its own packet framing, signature encoder (byte-equal with the vectors), lookup and SPEC 4.3 policy; rules go-crypto is laxer on (hashed issuer fingerprint, canonical key packets, v4 hash prefix) are checked on top. Secret keys: TS reads unprotected or iterated S2K + AES-CFB (gpg default); Go also reads Argon2/AEAD. A version 6 key needs a valid direct key signature (RFC 9580 5.2.3.10; vector `pgp-v6-no-direct-key.md`). Test keys in `examples/pgp/` (frank = gpg-made RSA, passphrase `test`); `scripts/pgp-interop.ts` checks against a real gpg (manual).
- Verification status vocabulary (shared by TS, Go, JSON): `valid | invalid | malformed | unresolved | unsupported`, codes `hash-mismatch | bad-signature | malformed | unknown-field | scope-missing | resource-mismatch | resource-missing | expired | revoked | key-changed | key-not-published | unsupported-version | unsupported-alg | unsupported-hash | unsupported-method | network | not-found | offline`.

## Extensions folded into v0.0.1 before release (2026-11-16)

All are in SPEC.md §5.6–5.9 and §6.1. The version string stays `0.0.1` because nothing has been published.

- **Unknown fields fail** (`unknown-field`); only `x_*` keys are free-form, so future extensions can never be silently accepted.
- **Folded `|` values keep LF** (lists). Binary values strip whitespace when decoded. In the payload, LF inside a value is written as LF + two spaces (no field forgery).
- `scope` (section markers `<!-- mdsig:section id -->` … `<!-- /mdsig:section -->`), `require` (exit code 5 = pending), `resources` (local always checked; https only on `--fetch-resources`; SSRF limits), `expires`, `revocation_url` (a signed list, see Format 0.1; trusted only from a block with the same `method` + `signer`, plus the same `pubkey` for tofu), `webauthn-es256` (passkeys; key type `es256`; `rp_id` is signed; DER sig converted to P1363 for Web Crypto).
- Passkey RP ID = `location.hostname` of the signing page (`keys.mdsig.dev` in production since the website moved, `localhost` in dev). Moving the signing pages to another domain orphans registered passkeys; passkeys made on the old `mdsig.dev` playground no longer work there.
- Test vectors for all of the above are in `examples/` (see `keys.json` `now` / `fetch`).

## Security review changes (2026-11-16)

Made after an adversarial review, before any release. All are in SPEC.md and both implementations, with vectors in `examples/`.

- **No `keyserver` field.** A block cannot name its keyserver (it is an unknown field now). A signer-chosen keyserver let anyone sign as someone else's email through a server that does not confirm addresses.
- **Revocation id = SHA-256(signed payload)**, not of the `sig` bytes. ECDSA (`s` → `n - s`) and OpenPGP (unhashed subpackets) signatures can be re-encoded without the key, which changed the old id. Helpers: `revocationId` (TS), `RevocationID` (Go).
- **A block with `scope` never satisfies `require`.** It does not cover the declaring block and stays valid when pasted into another document with the same sections.
- **Values reject** Cc, Cf (bidi controls, zero-width characters, tag characters), Zl, Zp and noncharacters (widened in format 0.1). The CLI also escapes control and format characters in human output.
- **`git-hosting` host** is a domain name of two or more labels; IP literals and `localhost` are malformed.
- **Limits**: a `tsa` block's `sig` decompresses to at most 1 MB, DER nesting at most 32, `genTime` must be a GeneralizedTime.
- **TOFU** bindings are stored only after the block verifies, never from a revocation list.
- **Go CLI**: every document-driven fetch (keys including `.keys` and DoH, WKD and keyservers, revocation lists, resources) uses `SafeHTTPClient`; the TSA request in `RequestTimestamp` uses the caller's client (`http.DefaultClient` when nil); local resources must be regular files inside the document directory (`os.OpenRoot`), at most 50 MB.
- **Playground**: document content in the preview carries no `style`/`class`/`id`/`data-*`/form controls; `applyStatic` never touches the preview; pages have a CSP.

- **Nothing unchecked counts as success.** `verify --offline` gives exit code 3 and `ok: false` when any block was not checked. A changed TOFU key is `invalid` / `key-changed` until accepted (`--accept-new-key`, core `acceptNewTofuKey`). A revocation list that cannot be fetched or is not signed by the signer makes the block `unresolved`; only `--offline` and `--no-revocation` leave it as a `not-checked` warning.
- **Chain length** is limited to 256 blocks (each block hashes the document from the start; Web Crypto has no streaming digest).
- **TSA**: an unverified token never shows a time. See the TSA entry above for the trust stores.
- **Release**: pushing a tag `vX.Y.Z` runs `.github/workflows/release.yml`: goreleaser builds all platforms, signs `checksums.txt` with cosign (keyless), writes SBOMs, publishes the GitHub release (not a draft, because the cask points at its assets) and updates the Homebrew cask in `SHIOZAKI-Shota/homebrew-tap` (pushed over SSH with a deploy key, secret `TAP_DEPLOY_KEY`; skipped with a warning when unset). winget (`ShiozakiShota.mdsig`, a portable zip) opens a pull request on microsoft/winget-pkgs from the `SHIOZAKI-Shota/winget-pkgs` fork when `DISTRIBUTE_TOKEN` is set; GoReleaser writes the en-US manifests and a workflow step adds the ja-JP locale from `.github/winget/` (GoReleaser's `additional_locales` writes `Moniker`, which the locale schema lacks). The first submission is microsoft/winget-pkgs#482729 (0.0.3, retitled "New package"); later ones are titled "Update: … to …". The repository variable `WINGET_PAUSED=true` skips winget (set 2026-11-19 until #482729 is merged; the 0.0.4 PR #484011 was closed); delete the variable to resume. A second job, `npm`, publishes `packages/core` as `@mdsig/core` through npm trusted publishing (OIDC, with provenance): `packages/core/package.json` must carry the tag's version (bump it before tagging), and a version already on npm is skipped. Releases of the CLI, the Go library and `@mdsig/core` share one version number. The first npm version (0.0.3) is published by hand, because trusted publishing can only be configured for a package that exists, as ClauseDown does. Checked locally with `goreleaser check` and `release --snapshot` (the generated cask installed and ran); the workflow itself, cosign and syft have not run yet. The cask removes the quarantine attribute after install because the binaries are not notarized; that step calls `/usr/bin/xattr`, so the cask is expected to fail on Homebrew for Linux.

## Server-side use (2026-11-17)

md-signature is built as a library first; the playground is one consumer.

- **HTTP API** (CLI_SPEC 3.6): `POST /v1/verify`, `POST /v1/tsa`, `GET /v1/health`. Served by `mdsig serve` (Go, `mdsig/server.NewHandler`) and by `createVerifyHandler` in the TS core (`src/server.ts`, any runtime with Request/Response). Both answer in the CLI JSON shape (`mdsig.ToJSON`, `toJsonResult`).
- **Per-request isolation**: no TOFU store, keyring or local files; Origin allow-list; JSON content type only; body and concurrency limits. Go fetches through `SafeHTTPClient`. The TS handler wraps fetch in `publicHostFetch` (refuses IP literals, localhost and internal names, follows redirects by hand); it cannot see what a name resolves to, so deployments with internal network access need egress rules as well.
- **Partial offload**: `VerifyOptions.tsaVerifier` replaces the token check (`remoteTsaVerifier(url)`); `fetch` and `resolvers` were already pluggable. An unverified result never keeps a `genTime`, whatever the verifier returned.
- **Two verifiers**: `remoteVerify(url, text)` plus `compareResults(local, remote)` report per block whether status/code and `tsa.verified` agree. Verdicts are shown side by side, never merged.

## Library evaluation (2026-11-17)

The user asked to move hand-written crypto to libraries where a library can do the job. Outcome, from spikes against the real vectors:

- **Go OpenPGP → ProtonMail/go-crypto**: done (see the pgp entry). 56,016 mutated signatures/certificates gave no valid/not-valid difference against the previous code.
- **Go CMS**: kept. `digitorus/timestamp` + `pkcs7` are laxer on every rule here (SHA-1, optional signed attributes, several SignerInfos, no ESSCertID) and have no tagged releases.
- **TS X.509/CMS**: kept. pkijs accepted 11 of the 24 forged tokens in `test/tsa.test.ts` and failed a real DigiCert token.
- **TS OpenPGP**: kept. OpenPGP.js agrees with our code on the vectors but is LGPL-3.0+, which would put LGPL code in an MIT package. Using it as a dev-only oracle for differential tests has no license problem and is an open item.

## Go public API (2026-11-17)

`mdsig` exported 139 top-level identifiers after the cleanup (195 before; format 0.1 added the agreement, signature-table, roster and explain types). The rule: export what `internal/cli`, `mdsig/server` or a library user needs; everything else is unexported, because adding an export later is compatible and removing one is not.

- Exported: signing and verifying (`SignDocument`, `VerifyDocument`, their options and results, status/code constants), extension points (`Resolver`, `TofuStore`, `ResourceLoader`, `SafeHTTPClient`, `TSAVerifyOptions`, `LoadTSARoots`, `DefaultResolvers`), signers, document inspection (`ParseDocument`, `ComputeBlockHash`, `SignedPayload`, `RevocationID`, scope/require helpers), key helpers the CLI uses, the JSON shape (`ToJSON`), and building blocks for custom resolvers (`DNSName`, `DNSKeysFromRecords`, `GitHostingKeysFromText`).
- Unexported: encoding helpers (use `encoding/base64` and `encoding/hex`), normalization and serialization internals, DER/CMS/TimeStampReq, WebAuthn encoding helpers, the individual resolvers, the fence scanner, regex variables.
- Naming: initialisms are upper case (`PGPSigner`, `ResolveOptions.PGPClient`, `TSAOK`). One function per job with an optional options pointer (`CheckTSAToken(token, data, nil)`, `RequestTimestamp(ctx, data, url, client, nil)`), no `…With` variants.
- No exported function, method or field mentions an unexported type, and the only exported variable is the sentinel `ErrForbiddenAddress`.

## Format 0.1 (2026-11-27, branch feat/format-0.1, release v0.1.0)

A breaking cleanup made while users are few (an IETF-reviewer pass of 20 items is folded in). Everything is in SPEC/CLI_SPEC and both implementations, with vectors in `examples/` (all 0.0.x vectors deleted).

- **Grammar (SPEC 3.2):** `v: 0.1` only (5.4 step 1: any other single `v` is `unsupported-version`). `alg` required, no `hash`/`alg` defaults. Values forbid `-->`, `--!>`, `<!--` (not `--`). Continuation line = two spaces + value; extra leading spaces are part of the value, trailing spaces are malformed. `role` is one word `[a-z0-9][a-z0-9._-]*`. Not YAML: every value is a string (`v: 0.1` would become a number).
- **Identifiers (SPEC 3.4):** canonical forms compared exactly (`sameSigner` removed). `ldh-domain` = RFC 1123 + A-label syntax, lower-case ASCII, checked by syntax only (no IDNA tables); U-labels may be shown when IDNA2008 and single-script. `git-hosting` user names lower-case; no `*` in any signer; `pubkey` compared as decoded key bytes (raw or SPKI). Generators lower-case ASCII except for `tofu`.
- **List lines (SPEC 3.5):** `scope`, `resources`, `require` share `target *(SP name[=value])`: single spaces, value split at the first `=`, unknown/duplicate/ill-formed attributes malformed. `scope` lines are bare section ids (no `section:`). `resources` lines are `<ref> hash=sha256:<hex>`; local refs are percent-decoded (`%2F`, `%5C`, `%00`, invalid UTF-8, `.`/`..`/empty segments malformed; `./x.png` is malformed and generators strip `./`); remote refs used as written.
- **`require` (SPEC 5.8, Appendix C):** ABNF with `order mode=pending|guide|strict`, `step [any=m]`, indentation optional (generators indent step members by two spaces). Attributes `role=`, `user_verified` (`dns`, `directory`, `tofu` with `pubkey=`; WebAuthn UP+UV, `crossOrigin` true rejected), `member_of=<https URL | dns:domain>`, `pubkey=` (tofu lines, SHOULD; warning without it). Closed pattern list `dns:*`, `dns:*.<d>`, `directory:*`, `directory:*@<d>`, `pgp:*`, `pgp:*@<d>`, `git-hosting:*` (label-boundary matching; patterns never count the declarer). `strict` with pattern lines is malformed. Assignment is deterministic: per step, the earliest prefix where max-flow reaches m (or fills every line), reported via Kuhn's algorithm with signers in order of first eligible block and lines in declaration order; blocks used by a step are not reused by later steps of the same declaration. Unknown methods/attributes keep the block valid and make the agreement `unsupported`.
- **Rosters:** https rosters are signed lists `type: members` issued by `dns:<URL host>`; DNS rosters are TXT `v=mdsig1; m=<method:signer>` at `<base32lower-nopad(SHA-256("md-signature/member/v1" LF id))>._member._mdsig.<domain>` (the `m=` match defeats wildcard records; NXDOMAIN/NODATA = not a member, SERVFAIL/timeouts = undetermined). DNS selectors may not start with `_`. Helpers `memberRecordName` / `MemberRecordName`, CLI `mdsig member-record [--check]`. Limits: 64 lines, 16 steps, 8 roster URLs, 256 lookups (exceeding them gives undetermined, not malformed).
- **Agreement statuses:** `none | complete | pending | violated | undetermined | unsupported`. `undetermined` (roster or network missing) → exit 3; `violated` and `unsupported` → exit 1; all three give `ok: false`. JSON: `attributes` object, `rejected: [{index, reason}]` (reasons `early | blocked | not-member | roster-unavailable | not-user-verified | key-mismatch | self | scoped | not-valid`, a vocabulary separate from block codes), `next`, `satisfied`, `declarations`.
- **Signed lists (SPEC 5.10):** revocation lists and rosters put their entries in exactly one fenced block with info string `mdsig-list` (`type: revocation` + `revoked: sha256:<hex>`, or `type: members` + `member: <method:signer>`). https only, 10 MB, cached per verify call, verified with revocation/resources/agreement off, trusted only from an unscoped valid block of the expected issuer; verifiers must handle 100,000 entries. Any bad line, wrong type, or zero/two fences → untrusted.
- **Timestamps (SPEC 4.6):** `tsa` blocks only (`tsa_url`/`tsa_token` removed; `sign --tsa` / `tsaUrl` append a `tsa` block). `T(k)` = min over later valid `tsa` blocks of `genTime + accuracy`; used by JSON `signatures[].tsa` (`time`, `block`), key-snapshot times and the signature table. Renewal chains are not verified in this version.
- **Display and table (SPEC 3.3, 5.11, 9.5):** `display_name` (RFC 8266 Nickname, ≤ 64 code points, always shown with the verified signer and marked as declared). `<!-- mdsig:signatures -->` marks where viewers draw the table; first marker outside fences wins, others warned; nothing is written into the body, and the table is built outside the sanitized body DOM. `signatureTable` / `SignatureTable`, `renderSignatureTableHtml` / `RenderSignatureTableHTML`, CLI `mdsig render`.
- **Fence scanning (SPEC 5.5):** a normative line scanner (0–3 spaces, ≥ 3 backticks or tildes, closed by the same character and at least the same length) for section markers, the table marker, stray-marker detection and `mdsig-list` fences. A body that ends inside an open fence: signers refuse, verifiers warn.
- **Usability:** `explainRequire` / `ExplainRequire`, `mdsig require explain` (ja/en, `--json`); hints (not verdict changes) for positional roles, `order strict`, `step 1`, `section:`, old `resources` order, `tsa_token`, `v: 0.0.x`. Passkey signing asks for `userVerification: "required"` when a pending line needs `user_verified`; the handoff carries `user_verification=required` and both sides refuse a result without UV (CLI_SPEC 8).
- **Removed:** `tsa_token`/`tsa_url`, the `zstd+base64:` reservation, every 0.0.x rule (legacy `require`, mixed versions).
- **Agent commerce:** `AGENT_COMMERCE*.md` (informative) maps LCP (`atrHash` = the accepting block's `hash`), x402 (`accepts[].extra.atrHash`), AP2 and PACT; recommends a named final-confirmation step after pattern/roster steps, and no `expires` for offers. Guide page `/docs/agents/`.
- **Deferred:** `by=` requirement deadlines (after time-evidence rules settle), an MCP server, a JSON Schema for the CLI output, a hint for hash mismatches that differ only in whitespace, `prefixDigest`, body indentation normalization.

## Key directories and `method: directory` (2026-11-18, release v0.0.4)

- **What**: a signer without a domain signs as a lower-case email address; the key comes from a key directory that confirmed the address (SPEC 4.7, KEY_DIRECTORIES.md). keys.mdsig.dev is one directory, not an authority.
- **Which directory**: never from the block (a signer-chosen directory lets anyone claim any address, the same reason the `keyserver` field was removed). First the `dir=` tag of the `v=mdsig1` TXT record at `_mdsig.<email domain>` (several different values: unresolved/not-found); otherwise the verifier's trusted list (default `https://keys.mdsig.dev`; TS `keyDirectories`/`extraKeyDirectories`, Go `ResolveOptions.KeyDirectories`, CLI `mdsig directory trust add|list|remove` stored in `<config>/mdsig/key_directories.json`, plus `--key-directory`).
- **Lookup**: `GET <dir>/v1/keys/<sha256(email) hex>`, JSON `{email, verified, keys:[{type,key,added}]}`; a response for another `email` counts as no key; 404 = not-found, failures = network. Directories must send `Access-Control-Allow-Origin: *`. The DNS tag rules now say unknown tags are ignored (existing parsers already did).
- **Snapshot** (SPEC 4.5; `dns`, `git-hosting`, `directory` may carry `pubkey`; embedded key checked first, valid only if still published, otherwise `unresolved` / `key-not-published`): `directory` is a key-snapshot method; generators embed `pubkey` by default (TS `embedKey` defaults to true for directory, Go `OmitKeySnapshot`, CLI `--no-embed-key`).
- **Registration** (keys.mdsig.dev API, not the format): `POST /v1/challenges`, `POST /v1/registrations` with a proof over `md-signature/keydir/v1\n<challenge>\n<email>\n<type>:<key>` (Ed25519 signature, or a WebAuthn assertion whose challenge is SHA-256 of it), confirmation by email, `POST /v1/removals`. TS `directory.ts` (`createRegistration`, `verifyRegistration`, `registerWithDirectory`), Go `RegisterKey`, `RequestKeyRemoval`, CLI `mdsig directory register|remove`.
- **Removal with the key itself** (release v0.1.2): `POST /v1/removals` with `challenge` and `proof` over `md-signature/keydir/remove/v1\n<challenge>\n<email>` (no key in the message; the directory removes the registered key the proof verifies with, so a passkey works without knowing its public key) removes at once, no email. Email removal stays for lost or stolen keys. - **Server**: repository `mdsig_kds` (Hono; deployable on its own with a confirmation page and a policy template; the website `mdsig_dot_dev` embeds it behind `keys.mdsig.dev/v1/*`; D1 `mdsig-kds`; Email Service from `noreply@keys.mdsig.dev`; Workers logs off), next to its pages (`/keys/`, `/register`, `/remove`, `/confirm`, `/policy`). Passkeys made there use RP ID `keys.mdsig.dev`. Confirmation links are `/confirm#<token>`, confirmed by a button (link scanners cannot confirm). Labels are stored, never published or mailed.
- **TOFU (SPEC 4.4, CLI_SPEC 3.9)**: a binding is written only after every check of the block passed (expiry, resources, revocation included), and a first-seen key gets the warning `tofu: no stored key for signer …`. `mdsig known list|remove`; writers of `known_signers.json` reread it just before writing and keep it 0600. ## Writing style (Japanese and English) — applies to every document and UI string

The author is Japanese. Japanese text is written first and should read like careful technical Japanese, not like generated text.

**Japanese: prefer 熟語 (Sino-Japanese compounds) over 和語 when the compound is natural in technical or legal writing.**
Examples: 使う→使用する, 作る→作成／生成する, 確かめる→確認する, 調べる→検証する, 書き換える→改変／変更する, 付ける→付与する, 渡す→受け渡す, 選ぶ→選択する, 消す→削除する, 残す→保持する, 送る→送信する, 決める→決定／規定する, 始める→開始する, 表示は何も変わらない→表示に影響しない.
Do not force it: keep 和語 where the 熟語 would sound stiff or odd (e.g. 「1つのまま」「あとから」). UI labels are short noun phrases (「ファイル添付」「鍵ペア生成」「署名・追記」).

**Terminology (unified 2026-11-18):** Japanese katakana drop a trailing ー (サーバ, ユーザ, レンダラ); digits attach to counters (3人, 8件, 32文字); full-width （）and ：in Japanese prose. English is American spelling with the Oxford comma, "timestamp token", "key resolution". TSA = 時刻認証局; withdrawing a signature (`revocation_url`) = 撤回, revoking a key or certificate = 失効; `/playground/` is デモ in Japanese and "playground" in English.

**Avoid the known tells of AI-generated writing** (both languages):
- Long dashes (—) as a connector. Use 、 ： （ ） or two sentences. In English use a comma, colon, or period.
- 「A ではなく B」 / "not X, but Y" framing of a contrast nobody raised.
- Lists of exactly three by habit; padding a list to reach three.
- 「〜することができます」「〜と言えるでしょう」「〜を実現します」「さまざまな」「シームレス」「革新的」「強力な」「次世代」; English "seamless", "powerful", "robust", "delve", "crucial", "game-changer", "unlock".
- Inflated significance, vague authorities (「専門家によれば」), invented numbers.
- Bold labels at the start of every bullet; headings in "X and Y" pairs; closing summary paragraphs that repeat the text.
- Every paragraph the same length and rhythm. Vary it; say concrete things (what happens, to which file, with which key).

**Normative documents** (`SPEC*.md`, `CLI_SPEC*.md`): style edits must not change meaning, BCP 14 keywords (「〜しなければならない（MUST）」 etc.), identifiers, code, or section numbers.

## Code comments

Keep only section dividers (one line: `// --- title` in TS/Go, `// ------… title` / `/* ------… title */` in CSS) and minimal one-line comments where a reader cannot infer the reason from the code: a spec rule (`// SPEC 5.3: …`), a security reason, a workaround, a magic constant, a cross-implementation parity detail. No JSDoc/doc comments that restate names, no step-by-step narration, no comments in tests except dividers.
